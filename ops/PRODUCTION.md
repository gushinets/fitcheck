# FitCheck production: принятые настройки

Источник: публичный самостоятельный `gushinets/fitcheck`, ветка `main`.
Окружение — отдельный FitCheck production в существующем Dokploy.
Сайт — `https://fitcheck.dokploy.gcexp.ru`, новая PostgreSQL без переноса данных.
Первый запуск применяет все миграции создания схемы, включая `0016`.

## Анализы и расходы

В production-примерах API и worker зафиксированы:

```dotenv
FITCHECK_GUEST_DEMO_LIMIT=1
FITCHECK_ACCOUNT_ANALYSIS_DAILY_LIMIT=0
FITCHECK_BUDGET_ACCOUNT_DAILY_USD=0
FITCHECK_BUDGET_DEPLOYMENT_DAILY_USD=0
```

`0` снимает соответствующий лимит; положительное число включает его обратно.
Для гостевой квоты, бюджета отдельной задачи и остальных защит `0` недопустим.
В ответе `/v1/quota` отсутствие лимита и остатка представлено как `null`.
Счётчики резервов и выполненных анализов продолжают учитываться. Изменение квоты
аккаунта применяется к текущему окну после перезапуска API. Если новый предел уже
достигнут, новые анализы отклоняются до следующих UTC-суток; прежние задачи сохраняются.
После изменения денежных лимитов перезапустить и API, и worker.
Денежные окна продолжают учитывать расходы при `0`; возвращённый лимит проверяет
в том числе уже зарезервированный расход текущих суток. Бюджеты принятых задач
сохраняют исходный снимок ограничений.
Обычные настройки без production override сохраняют прежние ограниченные значения.

Сохраняются гостевой денежный бюджет, бюджеты отдельной задачи, ограничения токенов,
числа вызовов/повторов и одновременно выполняемых задач (гость — 1, аккаунт — 2).
Квоты подсказок и извлечения текста остаются прежними. Суточного денежного
предохранителя для аккаунта и сервиса нет; лимиты самого провайдера независимы.

## Продуктовая аналитика

`ops/env/api.env.example`, `worker.env.example`, `website.env.example` включают
production-аналитику. На API и worker заданы `FITCHECK_METRICS_ENABLED=true`,
`FITCHECK_METRICS_ENVIRONMENT=production` и
`FITCHECK_METRICS_DATABASE_ENVIRONMENT=production`. Сайт использует
`METRICS_ENVIRONMENT=production` и точный production origin в `ALLOWED_ORIGINS`.

Перед запуском заменить все шаблонные секреты. API `FITCHECK_METRICS_INGEST_KEY`
и сайт `METRICS_BRIDGE_KEY` должны совпадать. `METRICS_COOKIE_SECRET` — отдельный
случайный секрет. Реальные значения вводятся в runtime environment Dokploy,
не коммитятся и не передаются при сборке. Страница читает настройки во время запроса.

Для существующего HTTPS bridge выбран технический адрес коллектора
`https://fitcheck-api.dokploy.gcexp.ru`. Это планируемый маршрут, ещё не созданный
этими файлами. До запуска проверить DNS/TLS и маршрут к API, разрешить
`/internal/metrics/` только сайту с проверкой ingest key, а остальные приватные
эндпоинты закрыть снаружи. Product relay продолжает обращаться по `http://api:8000`.
Не включать development gateway, жёстко привязанный к `dev-fitcheck-api`, для production.

После запуска проверить фактические записи browser/server/lifecycle событий в БД
и их environment, а не только флаги или HTTP status. Отправка событий через bridge
работает best effort: временные сетевые сбои могут приводить к пропускам.

## Бэкапы и оповещения

По решению владельца бэкапы пока не запускаются. Том PostgreSQL остаётся постоянным,
но потеря этого тома или сервера приведёт к потере данных. Общий профиль `operations`
включает backup, поэтому пока нельзя запускать все сервисы этого профиля одним `up`.
Для мониторинга запускать только явно выбранный `prometheus` вместе с основными
сервисами. Подготовленный backup/restore smoke остаётся изолированным тестом.

Приложение экспортирует технические метрики, `ops/monitoring/alerts.yml` содержит
правила Prometheus. Alertmanager и доставка получателю пока не подключены;
`alertmanager.yml.example` — шаблон webhook. Канал и получателя выберем отдельно.

Полная инструкция сети, доверия IP и запуска — в `ops/RUNBOOK.md`.
Подготовка этих файлов и локальный commit не подключают Dokploy и не запускают деплой.
